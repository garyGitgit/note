We present an agent-maintained episodic memory system that captures structured debugging episodes from JIRA resolution threads and compiles them into a fixed-budget retrieval layer. Our key innovation is \textbf{LLM-compiled episodic retrieval}: a frontier LLM compiles each episode, once at admission time, into a semantic error type (17-class taxonomy), a canonical failure-mode gist, normalized keywords, a root-cause class, and duplicate clustering --- while query-time retrieval remains a deterministic, sub-millisecond index lookup with zero LLM usage, keeping the system operable in closed-network verification environments. A regex signature-based compiler is retained as an ablation baseline, and a knowledge-architecture evolution engine and an aggregated-knowledge inference layer (Top-K cluster voting with calibrated confidence, +5.0pp over single-reference prediction) complete the system. Under an identical chronological-replay protocol (901 evaluated queries), the LLM-compiled layer dominates every retrieval modality: 33.0\% Top-1 (66$\times$ BM25) versus 23.0\% signature-compiled, 19.2\% TF-IDF vector, 16.3\% graph-based (all $p<10^{-4}$, paired bootstrap), at 0.32\,ms latency with 0\% fallback. While many failures are unique, a substantial fraction are \textbf{recurrences} --- failures caused by root causes that have been previously diagnosed and resolved. Current practice relies on engineers manually searching JIRA databases, email threads, and shared documents to find relevant prior art, a process that is time-consuming, incomplete, and knowledge-fragile.Recent advances in retrieval-augmented generation (RAG) and long-context language models offer promising alternatives, but face fundamental challenges in the verification domain: (1) raw episode stores grow linearly with project lifetime, making exhaustive LLM context injection infeasible; (2) lexical search (BM25) misses structurally similar but lexically distinct failures; (3) vector-space and graph-based retrieval, while stronger than lexical search, remain bounded by the surface-form representation of episode text (Experiment I); and (4) stateless RAG approaches lack the \textbf{discriminative context} (design block, revision, configuration) needed to distinguish "same symptom, different cause" from "different symptom, same cause."We propose an \textbf{agent-maintained episodic memory system} with a \textbf{compiled retrieval layer} (Tier 0) that addresses these challenges through four design principles:\begin{enumerate}  \item \textbf{Immutable records, regenerable indices}: Episodes are append-only and never deleted; the compiled layer is regenerated on triggers (spec changes, block revisions, quality thresholds).  \item \textbf{LLM-compiled semantic matching}: A frontier LLM compiles each episode into a semantic error type, failure-mode gist, normalized keywords, and root-cause class at admission time; retrieval combines these semantic signals with block locality --- not just lexical similarity. A regex signature-based compilation is retained as a comparison baseline.  \item \textbf{Fixed-budget compilation}: The compiled layer occupies a constant token budget B regardless of store size, ensuring sublinear query cost.  \item \textbf{Evolving knowledge architecture}: Compilation weights, signal scores, schema fields, and index structures are not static --- the LLM continuously adapts them based on retrieval feedback, new error patterns, and changing design environments. The knowledge architecture evolves from a manually configured structure into an empirically optimized, self-improving system.\end{enumerate}\section{Related Work}\subsection{Retrieval-Augmented Debugging}Prior work on RAG for software debugging \cite{1,2} uses embedding-based similarity search over bug reports. These approaches treat bug reports as flat documents and rely on semantic embedding models that are typically unavailable in closed-network semiconductor environments. Our work differs by extracting \textbf{structured semantic signatures} (error type, block, root-cause class) via a one-time LLM compilation step, and using a lightweight deterministic index at query time --- no embedding model or external API is required on the retrieval path.\subsection{Vector and Graph Retrieval}Dense vector retrieval (FAISS, sentence encoders) and knowledge-graph retrieval are the two dominant alternatives to lexical search in general-purpose RAG systems. Under the constraints of a closed-network verification environment, we instantiate both as fully local baselines: TF-IDF vector search over episode text (a sparse vector-space baseline requiring no neural encoder), and 2-hop graph retrieval over a heterogeneous episode--block--error-type--keyword graph (a structural-relations baseline). Experiment I (Section 5.10) evaluates both under the identical chronological-replay protocol; both are dominated by LLM-compiled semantic retrieval, indicating that the bottleneck is not the retrieval data structure but the \textbf{semantic quality of what is indexed}.\subsection{Episodic Memory for Agents}The concept of episodic memory in AI agents \cite{3,4} stores agent experiences for future retrieval. Our work adapts this to the verification domain with domain-specific episode schemas (applicability context, root cause categorization) and a compilation step that extracts discriminative features.\subsection{Verification Knowledge Management}Commercial tools (e.g., Synopsys VC Execution Manager, Cadence vManager) provide regression tracking but lack structured root cause capture and recurrence detection. Academic work on verification knowledge bases \cite{5} focuses on specification traceability rather than operational debugging episodes.\section{System Architecture}\subsection{Three-Tier Storage}\begin{verbatim}Tier 0: Compiled Layer (fixed budget B=320 tokens)    |-- sig_index: sig_hash -> [episode_ids]    |-- block_index: block -> [sig_hashes]    |-- error_index: error_type -> [sig_hashes]    |-- block_error_index: block -> error_type -> [sig_hashes]  (v2)    |-- keyword_index: keyword -> [sig_hashes]                  (v2)Tier 1: Episode Store (append-only, immutable)    |-- 1,237 episodes, ~515 KB total    |-- Structured schema: signature, root_cause, applicability, evidenceTier 2: Raw Evidence Archive (content-addressed, retention-managed)    |-- Full logs, waveforms (FSDB/VCD), simulation databases    |-- Key excerpts preserved in Tier 1 episodes\end{verbatim}\subsection{Episode Schema}Each episode captures:\begin{itemize}  \item \textbf{Signature}: error\_type (enum: assertion\_failure, timing\_violation, hang, result\_mismatch, etc.), sig\_hash (MD5), assertion messages  \item \textbf{Root Cause}: type (RTL Issue, Specification, False Alarm, etc.), mechanism description, RTL snippets  \item \textbf{Applicability}: block (BLK\_DBG, BLK\_CPUCL0, etc.), revision range, configuration, tool environment  \item \textbf{Relations}: VAN references, supersedes/cites links  \item \textbf{Evidence}: log excerpts, waveform pointers, key signal traces\end{itemize}\subsection{Compilation Engine (\texttt{compile\_episodes.py}, \texttt{merge\_llm\_compiled.py})}The compilation engine distills the episode store into a fixed-budget retrieval layer. We evaluate two compilation methods under an identical retrieval protocol and token budget:\textbf{Proposed: LLM-based semantic compilation.} At episode admission, a frontier LLM\footnote{Compilation was performed with a large-scale instruction-tuned language model available inside the closed-network environment (a Qwen-class model, run via batched prompting under the task contract of \texttt{TASK\_SPEC.md}); the compiled layer is persisted, so results are reproducible without re-running the LLM. We use ``frontier LLM'' to denote any LLM of comparable instruction-following quality; the architecture is model-agnostic at query time.} reads each episode's summary, symptom description, root-cause mechanism, and assertion excerpts (including Korean-language discussion, which it normalizes into English), and produces a compiled entry with five semantic fields:\begin{enumerate}  \item \textbf{Semantic error type} from a controlled 17-class taxonomy (e.g., \texttt{sfr\_access\_violation}, \texttt{connection\_missing}, \texttt{clock\_freq\_mismatch}, \texttt{hang\_deadlock}) --- replacing regex error-type detection.  \item \textbf{Failure-mode gist}: a one-line canonical English description of the failure essence.  \item \textbf{Symptom keywords}: 2--8 normalized, de-duplicated keywords spanning signal names, IP components, and mechanisms.  \item \textbf{Root-cause class} from an 8-class taxonomy (\texttt{rtl\_bug}, \texttt{spec\_definition}, \texttt{waiver\_missing}, \texttt{maturity}, \texttt{false\_alarm}, \texttt{env\_setup}, \texttt{integration}, \texttt{unknown}).  \item \textbf{Canonical clustering}: near-duplicate episodes (same block, same failure essence) are linked to a canonical representative, enabling deduplicated retrieval.\end{enumerate}The LLM judges episodes by \textit{meaning} rather than keyword presence: on our corpus, 39.6\% of episodes (490/1,237) are misfiled by the regex classifier into an uninformative ``other'' bucket, whereas the LLM assigns all of them to discriminative semantic types. Query-time retrieval remains deterministic and fast: a single LLM call per incoming failure produces its semantic signature, after which matching against the compiled index is a pure in-memory lookup. The LLM is therefore used \textit{only at compile/ingestion time}, preserving closed-network operability and stable query latency.\textbf{Baseline: signature-based compilation.} The signature-based pipeline scores episodes by three regex-derived criteria with configurable weights: (1) \textbf{Distinctness} (w=0.4): uniqueness of the episode's root-cause signature (rare sig\_hashes score higher); (2) \textbf{Discriminability} (w=0.35): richness of applicability context (block + revision + config); (3) \textbf{Recency} (w=0.25): exponential decay with 365-day half-life. Entries are keyed by structural sig\_hash (MD5 of error type + keywords + signal paths) and greedily selected until budget B is exhausted. At B=32,000 tokens and \textasciitilde{}10 tokens/entry, up to 3,200 entries can be accommodated --- far exceeding our 1,237-episode store. This pipeline requires no LLM and serves as the comparison baseline in Experiment H.\textbf{LLM-compiled layer structure.} The LLM-compiled layer occupies the same fixed budget (\textasciitilde{}30 tokens/entry, 37.1K tokens for 1,237 entries) and exposes five indices mirroring the baseline's structure: \texttt{semantic\_index} (semantic type $\rightarrow$ episode IDs), \texttt{block\_error\_index} (block $\rightarrow$ semantic type $\rightarrow$ episode IDs), \texttt{keyword\_index} (2,421 normalized keywords), \texttt{rc\_index} (root-cause class), and \texttt{cluster\_index} (canonical $\rightarrow$ duplicates).\subsection{Knowledge Architecture Evolution Engine (\texttt{evolve\_knowledge.py})}While the compilation and retrieval mechanisms described above provide strong baseline performance, their static configuration --- fixed weights, hardcoded signal scores, and a predefined schema --- cannot adapt to shifting failure distributions, new design blocks, or evolving tool environments. If \texttt{block\_error\_type} precision is high, increase discriminability weight. If \texttt{sig\_hash\_exact} precision dominates, increase distinctness weight. Apply momentum-based update: \texttt{new\_weight = $\alpha$ $\times$ observed\_optimal + (1-$\alpha$) $\times$ old\_weight}, with $\alpha$=0.7.  \item \textbf{Evolve Signal Scores}: For each matching signal, compute precision = (correct matches) / (total fires). Signals with precision > 0.5 get score increases proportional to (precision - 0.5); signals below 0.5 get proportional decreases. Scores are clamped to [0.1, 1.0].  \item \textbf{Propose Schema Extensions}: Scan the episode corpus for recurring patterns suggesting new discriminating dimensions. Candidates include tool version strings (VCS, Verdi, SpyGlass), clock domain identifiers, testbench component names, random seed values, and regression tags. Proposals are ranked by discriminative power (high/medium/low) and require minimum support of 10 episodes.  \item \textbf{Propose Index Restructuring}: Analyze query access patterns from recent feedback. If queries frequently co-filter by (block, keyword), propose a \texttt{block\_keyword\_index}. If patterns shift toward (error\_type, tool\_version), propose the corresponding composite index.  \item \textbf{Refine Error Taxonomy}: Analyze queries classified as "other" (52\% of current queries) to discover new error types. Candidate types --- protocol\_violation, clock\_domain\_crossing, formality\_mismatch, synthesis\_mismatch, power\_analysis, coverage\_hole --- are promoted when $\geq$5 matching samples are observed. Confidence thresholds are adjusted per-type: raised when precision < 0.3 (more selective), lowered when precision > 0.7 (broader capture).  \item \textbf{Evolve Aggregation Rules}: Adapt the multi-episode aggregation parameters (Section 3.5) to observed retrieval outcomes. When the Top-3 vs Top-1 correctness gap is large, deeper candidates are relevant and the aggregation window widens (top\_k increases); when block-scoped queries show high precision, block-local pattern agreement is trusted more (block\_local\_weight increases); when the compiled layer is sparse (low hit rate), the suggestion confidence threshold loosens.\end{enumerate}\textbf{Architecture Versioning.} Each evolution run produces a new architecture version (semantic versioning: MAJOR.MINOR.PATCH). The architecture state --- weights, scores, schema, indices, taxonomy --- is persisted as \texttt{knowledge\_architecture.json} with a complete evolution history log. This enables: (a) rollback to any prior version, (b) A/B comparison of architecture versions, and (c) audit trail for compliance-sensitive verification environments.\textbf{LLM Role.} In the current closed-network implementation, statistical analysis serves as an LLM proxy for evolution decisions. The architecture is explicitly designed so that an LLM can replace statistical methods when available: the same interfaces (\texttt{propose\_schema\_extensions}, \texttt{evolve\_compilation\_weights}, etc.) accept LLM-generated decisions. An LLM would bring qualitative reasoning --- e.g., understanding \textit{why} clock domain crossing failures cluster in specific blocks --- that pure statistical analysis cannot provide.\subsection{Aggregated Knowledge Engine (\texttt{aggregate\_knowledge.py})}Single-reference retrieval --- returning the RCA and solution of the one best-matching past episode --- has three structural weaknesses: it is vulnerable to a single noisy match, it cannot express generalized patterns ("X-type failures in this block are usually caused by Y"), and it provides no calibrated confidence. The \textbf{aggregated knowledge engine} addresses these by aggregating knowledge across the Top-K retrieved episodes instead of trusting a single hit:\begin{verbatim}Query → Top-K Retrieval (chronologically filtered)      → Cross-Episode Pattern Mining      → Confidence Calibration      → Knowledge Distillation      → Aggregated Suggestion (RCA + rules + confidence)\end{verbatim}\textbf{Layer 1 --- Cross-Episode Pattern Mining.} The retrieved cluster is mined for vote-weighted root-cause frequency distributions (each episode votes proportionally to its retrieval score and recency), block-local distributions (episodes from the same design block), error-type-scoped distributions (episodes sharing the query's error category across blocks), and mechanism co-occurrence patterns in solution descriptions. Root cause types are normalized to base categories ("RTL Issue - Fixed" $\rightarrow$ "RTL Issue") so the aggregation operates on cause categories rather than resolution outcomes.\textbf{Layer 2 --- Confidence Calibration.} The prediction confidence combines two consistency signals: \textit{block-local consistency} (do episodes from the same block agree on the root cause?) and \textit{global consistency} (does the whole cluster agree?). Cluster disagreement is measured as normalized entropy over the vote distribution and penalized, so a cluster of five episodes split across four different root causes yields low confidence even when the majority vote is clear. Block-local vs. global weighting is itself an evolvable parameter (the aggregation rules dimension, Section 3.4).\textbf{Layer 3 --- Knowledge Distillation.} The aggregated cluster is distilled into generalized, auditable rules --- e.g., \textit{"[timing\_violation] failures are caused by 'RTL Issue' in 3/4 similar cases (cross-block)"} or \textit{"Solution pattern 'clock' appears in 5/7 similar episodes"} --- each carrying support counts and precision. Rules are scoped (block / error\_type / global / mechanism), giving the debugging engineer both a prediction and the evidence structure behind it.The entire pipeline is governed by eight evolvable parameters (\texttt{top\_k}, \texttt{min\_support}, \texttt{block\_local\_weight}, \texttt{global\_weight}, \texttt{divergence\_penalty}, \texttt{recency\_decay}, \texttt{confidence\_threshold}, \texttt{score\_weight}) that evolve through the feedback loop described in Section 3.4. Experiment G (Section 5.8) validates that aggregation improves root-cause-type prediction over single-reference inference by +5.0pp under identical candidate retrieval, and that these parameters evolve from the prediction outcomes themselves through per-parameter credit assignment --- with demonstrated convergence (Section G.6b).\section{Multi-Signal Compiled Retrieval}Both compiled layers (LLM-compiled and signature-based) use the same retrieval principle: a cascade of discriminative signals scored by priority, with BM25 fallback to Tier 1 when the compiled layer yields fewer than K results. The \textbf{signature-based} layer (the Experiment H baseline) matches regex-derived structural hashes; its signals are described first for reference. The \textbf{LLM-compiled} layer (the proposed method) matches semantic types, root-cause classes, and normalized keywords; its scoring is detailed in Section 7.2.\subsection{Query Signature Extraction}When a new test failure arrives, we extract its error signature using the same pipeline as episode creation:\begin{enumerate}  \item \textbf{Error type classification}: Regex patterns detect assertion\_failure, timing\_violation, hang, result\_mismatch, x\_propagation, power\_issue, reset\_issue, parity\_error  \item \textbf{Keyword extraction}: Domain-specific keywords (assertion, timing, clock, reset, SFR, BIS, AXI, etc.)  \item \textbf{Signal path extraction}: Hierarchical signal paths from error messages  \item \textbf{Sig\_hash computation}: MD5(error\_type | keywords | signals)\end{enumerate}Extraction achieves \textbf{100\% success rate} on our 200-query test set.\subsection{Five-Signal Matching}The compiled layer retrieval uses a cascade of five matching signals, scored by discriminative power:\begin{table*}[!t]\centering\small\setlength{\tabcolsep}{3pt}\resizebox{\textwidth}{!}{%\begin{tabular}{|l|l|l|l|}\hline\textbf{Priority} & \textbf{Signal} & \textbf{Score} & \textbf{Description} \\\hline1 & sig\_hash\_exact & 1.0 & Exact structural hash match \\2 & block+error\_type & 0.8 & Same design block AND same error category \\3 & keyword & 0.3-0.6 & Overlapping domain-specific keywords \\4 & error\_type\_only & 0.45 & Same error category (cross-block) \\5 & block\_only & 0.25 & Same design block (coarse fallback) \\\hline\end{tabular}%}\end{table*}Results are scored and sorted by the highest-priority match. If fewer than K results are found, BM25 lexical search on Tier 1 episodes fills the remaining slots. The hybrid method (Method 6) uses Reciprocal Rank Fusion (k=60) to merge compiled and BM25 results.\subsection{Implementation}The retrieval engine (\texttt{retrieve\_episodes.py}, \texttt{retrieve\_llm\_compiled.py}) implements 10 methods:\begin{itemize}  \item \textbf{Method 1 (bm25)}: Pure lexical BM25 baseline  \item \textbf{Method 2 (rag)}: BM25 + domain-specific reranking (block, error\_type, keyword boosts)  \item \textbf{Method 3 (long\_context)}: Simulated LLM context injection (BM25 proxy)  \item \textbf{Method 4 (raw\_episode)}: Block-filtered BM25 on raw episodes  \item \textbf{Method 5 (compiled\_episodic)}: Multi-signal matching over the signature-based compiled layer $\rightarrow$ Tier 1 fallback  \item \textbf{Method 6 (hybrid)}: RRF fusion of compiled + BM25  \item \textbf{Method 7 (aggregated\_episodic)}: Top-K cluster $\rightarrow$ pattern mining $\rightarrow$ confidence calibration $\rightarrow$ distilled rules (Section 3.5)  \item \textbf{Method 8 (llm\_compiled)}: Multi-signal matching over the LLM-compiled semantic layer --- the proposed retrieval method (Sections 3.3, 7.2; Experiment I)\end{itemize}\section{Experimental Evaluation}\subsection{Dataset and Protocols}\begin{itemize}  \item \textbf{Episodes}: 1,237 extracted from production JIRA issues (VAN project), spanning 2025-08 to 2026-10  \item \textbf{Queries}: 1,117 gold-labeled test issues from dataset\_A\_gold\_labeled.json  \item \textbf{Recurrence pairs}: 129 VAN reference pairs (van\_recurrence\_pairs.json)\end{itemize}\textbf{Evaluation protocol.} All retrieval experiments use one chronological-replay protocol: each past episode, in turn, is treated as an incoming failure;
