Multi-Agent Orchestration
for Autonomous Regression Management 
Sangwoo Noh1, Jin Choi2, Seonghee Yim3, Youngsik Kim4
(1sangwoo.noh; 2jjin.choi; 3sh.yim; 4ys31.kim@samsung.com)

Abstract - The growing complexity of designs and limited compute resources have made regression management a critical bottleneck in modern verification. While regression automation pipelines have been introduced to mitigate this problem, they remain fundamentally linear, single-path processes in which failure and coverage information is siloed rather, so a human manager must relay it instead of having it directly drive future test planning and resource allocation. This manager-centric flow causes long turn-around time and persistent bottlenecks when designs or verification environments change. To address this, we propose an AI-driven, non-linear closed-loop regression flow where each regression run feeds back into the next decision cycle, dynamically reshaping scope, priorities, and scheduling. We implement this architecture with a multi-agent architecture: a central Orchestrator turns regression data into concrete control decisions, which specialized LLM agents then execute across triage, knowledge update, and resource-aware scheduling. Our work transforms regression automation from a procedural pipeline into an adaptive workflow that reduces overall regression turn-around time and strengthens design robustness at sign-off.

I.   INTRODUCTION
As modern digital designs grow increasingly complex, regression management has become the key constraint on verification throughput. Conventional automation pipelines improve repeatability but remain scripted, developer-defined, and effectively linear: regression data is routed through human managers who must monitor and plan tests, scripts, and schedules. This manager-centric workflow makes the human manager a throughput bottleneck: root-cause information from failures propagates slowly across owners, delaying issue resolution and triggering repeated regression reruns to rediscover and validate fixes. Even with automation in place (e.g., Jenkins), most regression flows remain scripted and execution-centric: the system can trigger and monitor runs, but it cannot interpret failures, route ownership, or translate outcomes into updated scope, priorities, and schedules.
These limitations suggest that regression management is not merely a linear pipeline problem, but a control problem: decisions must be continuously updated based on observed outcomes. In a closed-loop control system, outputs are fed back to adjust subsequent control inputs, allowing the system to regulate toward explicit objectives under changing conditions. We argue that design-verification regression fits this model because the results of each run should immediately guide the next actions: what to run next, what to prioritize, and how to allocate compute, without relying on a human manager to relay and interpret the information.
This paper makes four contributions to regression automation. First, we model design-verification regression as a non-linear, closed-loop control problem, rather than a linear, scripted pipeline. Second, we introduce a multi-agent orchestration approach for autonomous regression management, comprising specialized Planning, Execution, Monitoring, Debugging, and Notification agents coordinated by a central Orchestrator. Third, we present an end-to-end system design—agent I/O protocol, tool adapters, and safety policies—that enables the framework to adapt to dynamic regression environments with minimal human intervention. Fourth, we evaluate our approach against procedural and single-agent baselines, using regression turnaround time and coverage progress to quantify throughput, cost, and robustness.
II.   BACKGROUND
Closed-loop control system
A closed-loop control system has a few basic parts: goal, state, action and feedback. The goal specifies the desired target the system should achieve or maintain. The state denotes the system’s currently observed condition, typically represented by measured outputs or telemetry signals. The action is the intervention applied to the system to move it closer to the goal. The feedback path returns the measured state to the controller so it can compare the current condition against the goal and update future actions accordingly.
Design-verification regression maps onto the basic parts of a closed-loop system. The goal is defined by sign-off objectives—e.g., schedule milestones, achieving target coverage levels, and meeting quality thresholds such as failure-rate limits. The state is the current observed condition of the regression—coverage closure status, open failure backlog, runtime trends, and resource availability. The feedback is the stream of results returned by each run—failure logs and signatures, coverage deltas, pass/fail statistics, and queue/resource metrics—informing how far the current state deviates from the goal. The action is the set of control moves taken for the next cycle: selecting or pruning tests, adjusting priorities and scheduling, reallocating compute and licenses, triggering targeted reruns and routing issues to the appropriate owners. Together, these parts form a repeating loop in which each regression iteration updates the next plan based on observed outcomes.
Typically, human regression managers operate this loop as a sequence of scripted steps within a largely linear pipeline. They observe the status of ongoing regression processes, assess progress against the stated goals, triage failing cases, and then adjust test selection, constraints, priorities, and resource usage before launching the next run. However, this reveals a mismatch between the problem structure and the prevailing architecture. Closed-loop regression requires continuous re-planning under non-stationary conditions—frequent design changes, coverage gaps, and fluctuating queue and license availability—yet a static, linear pipeline can only react through manual edits and sequential handoffs. A better way to run this control loop is to make the “controller” distributed and flexible rather than centralized in one manager or one fixed script. In practice, different signals require different expertise—failure triage, coverage closure, and queue/resource management—so specialized agents can each track their own part of the state, share what they learn, and coordinate the next step. Our multi-agent orchestration replaces manual handoffs with tool-driven actions, so test scope, priorities, and scheduling can be updated immediately when new failures, coverage results, or resource constraints appear.

Agentic AI
An agent is an autonomous software entity that is responsible for a specific function, such as planning, execution, monitoring, debugging, or reporting. It considers only the information required for that function and interacts with the rest of the agents through structured inputs and outputs, under explicit policies and guardrails that constrain its actions. An agent consists of: (i) a role and responsibility specification that defines its objectives and decision scope; (ii) optional sub-agents that decompose internal skills (e.g., a log-summarization sub-agent within debugging and reporting); (iii) structured inputs and outputs that enable consistent communication among agents; (iv) tool adapters that safely invoke external systems; (v) an explicit communication topology that defines which upstream and downstream agents may exchange information; and (vi) guardrails that constrain actions and support auditability.
Single-agent systems rely on one generalized agent to interpret requests, maintain state, plan actions, invoke tools, and enforce policies end-to-end. While this design is simple to deploy, it becomes difficult to scale as task variety and system complexity grow. A single agent must accumulate and manage an increasingly large internal memory and context to remain consistent across decisions, which raises maintenance cost and can lead to unstable behavior, including inconsistent responses and hallucinated outputs as the prompt, tools, and policies evolve. Because decisions and actions are centralized, throughput is constrained by sequential processing and the agent becomes a single point of failure. Moreover, combining reasoning, tool execution, and policy enforcement in one component blurs responsibility boundaries, complicating least-privilege control, auditing, and debugging when behavior needs to be explained or corrected.
Multi-agent orchestration fits design-verification regression because regression is inherently a closed-loop process that must repeatedly convert outcomes into the next control actions under changing conditions. The loop must handle heterogeneous signals and time scales while adapting to frequent changes in RTL, testbenches, and toolchains, and operating under hard constraints such as limited compute and EDA licenses. 
A multi-agent system matches these requirements by assigning each function to a specialized agent with clear interfaces, coordinating their decisions through an orchestrator, and feeding results back to update scope, priorities, scheduling, and resource allocation each cycle.

III.   PROPOSED METHODS

A. Architecture
In this paper, we propose a multi-agent regression management system to address the challenges of design-verification regression. To make this design concrete, we decompose regression management into a small set of role-specific agents, each with a well-defined responsibility and interface. The Planning agent transforms project schedule, live resource status, and history into a deadline-feasible, prioritized test plan; the Execution agent turns that plan into least-privilege, environment-aware runs across heterogeneous tools; the Monitoring agent keep tracks of live states of tests, emitting failure evidence and replan triggers; the Debugging Agent converts failures into auditable diagnoses, creates bug reports, assigns issues to the most likely owners, and manages issue relationships; and the Notification agent disseminates outcomes to Jira/mail/messaging with access control and default manager visibility.
Coordination arises from typed, schema-checked messages; shared traceability that includes logs, commit hashes, and snapshots of queue and license state; and explicit guardrails such as deadline-first planning, design verification-scoped execution, and evidence-backed diagnosis, rather than from a central orchestrator. A lightweight Agent Registry supports dynamic discovery and capability negotiation, enabling plug-and-play onboarding of new agents such as classifiers and resource probes without destabilizing the system.

Debugging Agent: sub-agents, input, output, tools and guardrails
Debugging Agent converts failures into actionable and auditable outcomes—clear diagnosis, assigned ownership, and a minimal, reproducible ticket. It orchestrates specialized sub-agents to compress the space of evidence and decision. The ErrorSummarizer sub-agent condenses multi-GB logs into focused narratives and salient snippets. The Classification sub-agent labels failure types using learned and rule-based detectors so that downstream actions can be templated. The IssueSimilarityChecker sub-agent searches historical defect databases to find closely related bugs, enabling informed de-duplication and reuse of validated remedies. Ownership is decided by the Ownership sub-agent using a staged policy: it prioritizes similarity-based assignees, falls back to Git/Perforce blame and recent change density on relevant files, then consults ownership maps, and finally applies explicit rule-based routing when signals are weak. The Bug Report sub-agent emits a minimal ticket with summary, class label, reproduction command, and decision traceability links (logs, diffs, prior issues), while the Solution Agent surfaces grounded recommendations such as specific rerun flags or references to known fixes. 
Inputs include any user query, the error message, and testcase metadata (feature tags, log paths, implicated block/IP), plus run artifacts forwarded by Monitoring or Execution. Outputs are the named assignee and the bug report ID, accompanied by the structured diagnosis and rationale. The Debugging Agent uses tools such as file search/read, classification and similarity algorithms, Jira and VCS integrations, and mail/messenger hooks. 
It depends on Monitoring Agent for timely evidence and may ask Execution Agent for targeted re-runs with its evidence-backed parameters; Notification Agent later disseminates its outcomes. Its non-negotiable guardrail is no unsupported speculation: every solution suggestion or assignment must cite concrete artifacts; hallucinated fixes are prohibited, and all steps leave an audit trail.


Planning Agent: sub-agents, input, output and guardrails
Planning Agent serves as the system’s decision-making before starting regression, translating open-ended user requests and evolving project realities into a deadline-feasible and value-maximizing regression plan. It reasons simultaneously about tape-out/MTO (Mask Tape-Out), expected marginal coverage gain, historical error-proneness, and execution cost so that each selected testcase, seed, and configuration is justified against schedule and budget. 
Internally, it decomposes planning into three cooperating sub-agents. The Schedule sub-agent aligns proposed runs with calendars, freeze dates, and delivery gates, explicitly modeling hard windows and handoffs. The Resource sub-agent exposes a live picture of compute, license, and queue health, allowing the plan to prefer lower-latency resources when queues surge or to throttle demand when license pools tighten. The Planning sub-agent performs the core optimization by ranking tests, selecting seeds and configurations, and allocating time windows. It draws on schedule and resource views, a history tool that captures past outcomes, failure signatures, and coverage deltas, and design-change signals such as recent RTL or UVM edits. 
Inputs to the Planning Agent include the user query, project metadata, and the canonical testcase corpus. Its output is a timestamped, prioritized list of tests with intended start windows, selected seeds and configurations, and a brief rationale for each item. The agent grounds decisions through a testcase retriever, project schedule and regression-progress services, and LSF and license resource probes.

Planning Agent depends downstream on the Execution Agent to materialize the plan and upstream on Monitoring Agent and Debugging Agent to trigger incremental replans when new evidence arrives. The governing guardrail is deadline-first feasibility: the agent rejects requests that would breach schedule constraints and records the trade-offs behind that decision, for example when a proposed repetition adds cost without meaningful benefit.

Execution Agent: sub-agents, tools and guardrails
 Execution Agent turns plan intent into reliable, reproducible runs across heterogeneous backends while enforcing least-privilege boundaries. It is organized around two sub-agents. Command-Builder sub-agent converts abstract plan entries into environment-aware, tool-specific invocations by consulting tool guides and environment descriptors; it normalizes flags, paths, licenses, and seed handling so that different simulators/emulators are addressed consistently.  Execution sub-agent then submits and tracks jobs, manages safe retries, enforces dependencies, and packages artifacts including logs, waveforms, submission IDs, and exact reproduction commands. 
Inputs comprise the Planning Agent’s timestamped list, the chosen execution tool and environment, and the applicable guide; outputs report binary success/failure per job, augmented by pointers to collected artifacts. The Agent uses a workflow management tool and a command-execution tool to integrate with given workflow engines and resources. It depends on the Planning Agent for intent, streams progress to Monitoring Agent, and exposes artifacts to Debugging Agent for diagnosis; when Debugging Agent returns evidence-backed remedies (e.g., rerun with a specific flag), the Execution Agent supports targeted re-runs. 
Its guardrail is strict design verification scope: unauthorized commands, privileged shell actions, or ad-hoc system modifications are refused and logged, and all invocations are validated against tool guides prior to dispatch.

Monitoring Agent: roles, tools and guardrails
Monitoring Agent maintains the live status of regression. It continuously updates the state of each testcase—queued, running, passed, failed, or error-prone—and detects when an error has occurred. When a failure is observed, it emits a standardized failure event with minimal evidence and forwards it to the Debugging Agent. When a previously failing testcase turns green after a re-run, it marks the status accordingly and notifies the Planning Agent so the case can be re-scheduled if needed. It also aggregates simple progress views at suite and milestone levels to show how far the run is from plan
The functionality of tools used for Monitoring Agent includes reading from scheduler and workflow status APIs, consumes execution telemetry streams, and tails bounded log excerpts for first-error signals. It writes structured status records to a metrics store and exposes read APIs and dashboards for humans and peer agents. All heavy artifacts remain in external storage and are referenced by stable URIs.
Monitoring Agent is strictly read-only with respect to artifacts and execution state; it does not mutate logs, change job configuration, or infer remedies. It emits signals rather than prescriptions, attaches timestamps and provenance to every update, and rate-limits duplicate events. If upstream data are incomplete, it degrades to best-effort reporting without fabricating status.

Notification Agent: roles, input, output, tools and guardrails
 Notification Agent ensures that results reach the right stakeholders, on the right channels, with the right policy. It packages execution summaries, debug diagnoses, and status changes for delivery via JIRA, email, and messaging sub-agents, selecting recipients from ownership maps and watch lists and enforcing access control with manager visibility by default. 
Its inputs are reportable payloads emitted by Debug and Execution, augmented with audience context; its outputs are delivery receipts, message IDs, and links that are written back to the system’s decision traceability record for end-to-end traceability. The agent’s tooling consists of mail sender, messenger sender, and Jira post/update interfaces. 
It depends on Debugging Agent and Execution Agent and closes the loop by confirming dissemination. The guardrails are clear: distribute design verification -relevant content only, respect authorization rigorously, and avoid overexposure by scoping messages to need-to-know audiences while ensuring managerial oversight.

B. Technical Details
For agents to act meaningfully in a design-verification regression environment, each must operate over well-scoped context, invoke vetted tools, respect explicit policies/guardrails, and emit complete decision traceability. Our implementation treats these four elements as first-class concerns that cut across Planning Agent, Execution, Monitoring, Debugging, and Notification Agents.

Context. We distinguish between shared and local context. Shared context is the project-wide state that all agents may need to reference: goals and milestones, ownership maps, tool guides and policy documents, design-change signals, resource and license telemetry, prior regression outcomes, and aggregated coverage summaries. This state is maintained in a transactional context store and exposed as read-optimized views so that Planning Agents can rank tests promptly and monitors can render dashboards without contending for the same records. Local context is the working memory specific to a decision episode within an agent: the current task graph, typed inputs received via messages, intermediate features—such as classification confidences or expected marginal coverage estimates, and cached pointers to heavy artifacts. Heavy artifacts, for instance logs, waveforms, coverage databases, themselves reside outside the control plane in a content-addressed store and are referenced by URI; this avoids large payloads on the message bus and enables late materialization only for consumers that truly need the data. To prevent stale reads, messages carry schema versions and snapshot identifiers for source tables, and agents are required to reject or down-convert messages that fail validation.

Tools and MCP servers. In our implementation, all external integrations are exposed as tools on an MCP server, and agents act as MCP clients. Each tool advertises a typed request–response schema, a narrowly scoped permission set, rate limits, and audit logging. The server normalizes vendor specifics and enforces least privilege so that only documented verbs and flags are callable, while arbitrary shell execution and broad file-system access are unavailable. Results are returned as structured records, and heavy artifacts are written to content-addressed storage and referenced via stable URIs for later retrieval. Through this interface, the Planning agent queries testcase catalogs, project schedules, and live resource probes to produce a deadline-feasible plan; the Execution agent triggers DAGs and submits jobs, then returns reproducible artifacts and exact rerun commands; the Monitoring agent consumes telemetry and scheduler status streams to maintain per-test state and emit replan triggers; the Debugging agent reads files, runs classification and similarity analyses, consults VCS for blame and recent changes, and opens or updates tickets; and the Notification agent posts results to issue trackers, email, and messaging under access control, recording delivery receipts back into the system record.
The MCP layer also provides capability discovery and versioning, allowing new tools—such as a protocol-specific classifier or a GPU-license probe—to be added without rewiring peers. Schema validation at the server boundary rejects malformed calls and stabilizes evolution as tools and agents advance independently. Deny-by-default policies, per-tool scopes, and immutable audit logs create a governable surface, while provenance is preserved by attaching commit hashes, tool versions, queue and license snapshots, and artifact URIs to every call. This design keeps integrations safe and reproducible, reduces coupling between agents and vendor ecosystems, and enables the regression system to grow incrementally without sacrificing reliability or policy compliance.

Policy and guardrails. Policies are enforced as pre-decision checks at agent boundaries. The Planning Agent applies a deadline-first feasibility test and respects license/compute ceilings before producing a schedule; if a request would breach milestones, it returns a typed, rationale-bearing refusal rather than an infeasible plan. The Execution Agent validates every invocation against an allowlist derived from tool guides and runs in a sandboxed environment; unauthorized commands and privileged operations are refused and logged. The Monitoring agent is strictly read-only with respect to artifacts and does not infer fixes, preserving responsibility separation. The Debugging Agent imposes an evidence requirement for any diagnosis or remedy, supports abstention on low confidence, and records ownership rationales explicitly. The Notification Agent enforces least-privilege dissemination with manager visibility by default and excludes unauthorized content. Violations yield typed errors that upstream agents can handle (e.g., by replanning or downgrading a channel), ensuring graceful degradation rather than silent failure.

Interfaces and registry. Agents exchange typed JSON messages on a control plane with four parts: a header (id, type, time, producer, schema ref), a context block (project, variant, toolchain, milestone), a role-specific payload (plan, run status, failure evidence, diagnosis, delivery receipt), and a traceability block linking to artifacts and resource snapshots with stable URIs and a repro command. Schemas are versioned and validated at ingress and consumption so incompatible changes are rejected or safely down-converted. Each agent publishes an Agent Card—a signed manifest of capabilities, consumed/produced message types, supported schema versions, auth scopes, guardrails, endpoint, and health—registered over mTLS and discoverable via API/watch. The message bus provides at-least-once delivery with key-scoped ordering and dead-letter handling; consumers use idempotence and small de-dupe caches. Heavy artifacts live in content-addressed storage, referenced by digest URIs to keep messages small and decisions auditable.

C. Scenarios
The architecture can be exercised in the following scenarios. Subsequent sections will report simulation-based evaluations that quantify how effectively the system performs under each scenario introduced here, using both quantitative and qualitative measures.

Scenario 1. Failure triage and ownership assignment
When a testcase fails during regression, the Debugging Agent coordinates its sub-agents to produce evidence-backed diagnosis and ownership. The ErrorSummarizer sub-agent first condenses multi-GB logs into salient snippets and a concise narrative. The Classification sub-agent assigns a failure type (e.g., protocol violation, timeout, infrastructure). The IssueSimilarityChecker sub-agent searches historical tickets to detect duplicates or near-duplicates and links them to the current failure. Ownership sub-agent is then inferred by the Ownership sub-agent using a staged policy—(i) similarity-based candidate, (ii) Git blame and recent-change density, (iii) ownership-mapping fallback, and (iv) rule-based routing. The Bug Report sub-agent generates a minimal, reproducible report containing summary, class label, repro command, and decision traceability links, while the Solution Agent surfaces grounded remedies (e.g., rerun flags, references to validated fixes) when they exist. The outputs are the assignee and bug report ID, together with the diagnosis package. Guardrails prohibit unsupported speculation; every recommendation must cite concrete evidence (logs, diffs, prior tickets).

Scenario 2. Live regression monitoring and adaptive loop 
During ongoing regression, the Monitoring Agent maintains live system state by aggregating pass/fail outcomes, telemetry, and partial logs. It detects drifts (e.g., queue stalls, license starvation) and failure floods, emitting standardized events for downstream agents. On failure, Monitoring Agent forwards an evidence bundle—run parameters, log excerpts, decision traceability—to the Debugging Agent for rapid classification and ownership assignment. When Debugging Agent confirms a fix, or a targeted re-execution by the Execution Agent turns green, Monitoring Agent nominates the testcase back to the Planning Agent for re-scheduling to close coverage gaps or validate remedies. Throughout, Monitoring remains policy-neutral: it reports faithfully without mutating artifacts, thereby sustaining a stable closed-loop control system from execution → monitoring → debugging → planning.

Scenario 3. Deadline-aware planning and prioritization
When multiple testcases compete for limited resources, the Planning Agent constructs a schedule that is both deadline-feasible and value-maximizing. Its Schedule sub-agent incorporates project calendars and MTO milestones to define admissible time windows; its Resource sub-agent exposes real-time compute, license, and queue health; and its Planning sub-agent ranks tests by expected marginal coverage gain, historical error-proneness, and execution cost, integrating history and design-change signals. The output is a timestamped, prioritized plan (tests, seeds/configurations, intended start windows, and rationale) ready for consumption by the Execution Agent. The Planning Agent enforces a strict deadline-first guardrail—rejecting infeasible requests (e.g., excessive repetitions that would miss milestones) with explicit trade-off justifications—and performs incremental replanning as Monitoring/Debug evidence evolves.

IV.   RESULTS
We have designed and implemented an initial multi-agent regression management system in which the Planning, Execution, Monitoring, Debug, and Notification agents operate in concert. To assess whether this architecture yields practitioner-relevant gains, we will conduct a simulation-based evaluation across three core scenarios and a small set of stress variants such as license shocks, queue spikes, and bug floods. Each scenario will be exercised under controlled workloads with realistic compute and license budgets, injected design changes, and seeded instability.
For each run we will compare the multi-agent system against monolithic CI and single-agent baselines, measuring coverage per unit compute, time-to-assignee, triage precision and recall, time-to-result variance, and plan feasibility under deadlines. The simulation harness records full decision traceability, enabling apples-to-apples attribution of improvements to specific agents and policies. V.   CONCLUSION
 In conclusion, we reframed design verification regression as a closed-loop control problem and introduced a multi-agent architecture that replaces linear, script-bound pipelines with adaptive, goal-directed workflows. By assigning well-bounded responsibilities to Debugging, Planning, Execution, Monitoring, and Notification agents, and coordinating them through typed interfaces, guardrails, and provenance, the system reasons at the right decision horizons, executes with least privilege across heterogeneous tools, and diagnoses failures with evidence. This design directly addresses design verification realities—resource limits, non-determinism, and continual design churn—by enabling environment-aware test selection, marginal-coverage scheduling, error-prone suppression, accurate ownership assignment, and trustworthy dissemination. We implemented an initial system and specified operational and interface details suitable for deployment, together with an evaluation plan that measures practitioner-centric outcomes such as coverage per compute, time-to-assignee, triage precision and recall, and time-to-result variance against monolithic CI and single-agent baselines. The result is a modular and extensible verification workflow that adapts as conditions change while remaining auditable and safe.
